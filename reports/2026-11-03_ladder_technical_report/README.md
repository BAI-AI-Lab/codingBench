# codingBench 阶梯评测技术报告（2026-11-03）

评测对象：Kimi K3.1 Pro（另含 high 一组）、DeepSeek Flash V4.1-1017、MiniMax M3.1 Flash。论文：[main.pdf](main.pdf)。本报告按 arXiv 论文格式撰写，写法与 mmBench 技术报告（`BAI-AI-Lab/mmBench` 的 `paper/`）一致。下面的规则可复用于以后的评测报告。

## 构建

```bash
bash build.sh      # collect → analysis → 图 → 表 → xelatex + bibtex，输出 main.pdf
```

| 文件 | 作用 |
|---|---|
| `collect.py` | 从 `data/` 汇总逐个采样的得分与用量，生成 `paper_data.json`，只含题号与分数，不含题目内容 |
| `analysis.py` | 计算所有统计量，生成 `analysis.json` |
| `make_figures.py` | 生成 `figures/fig*.pdf`（同时生成 png，用于检查） |
| `make_tables.py` | 生成 `tables/*.tex` |
| `main.tex`、`refs.bib` | 正文与参考文献 |
| `site.py`、`site_assets/` | 生成公开网站 [bai-ai-lab.github.io/coding-eval](https://bai-ai-lab.github.io/coding-eval/)（仓库 `BAI-AI-Lab/coding-eval`），数字与 `main.pdf` 同源 |
| `fetch_statements.py` | 下载网站展示的官方英文题面（USACO 官网页面与图片、EGOI 2026 官方 PDF、FrontierCS 的 statement.txt，后两者钉在建库时的 commit）到 `data/statements_src/` |

网站：先 `python fetch_statements.py`，再 `python site.py <coding-eval 仓库目录>`，需要 `data/`、pygments 与 pdftoppm（poppler）；数学公式用 `site_assets/katex/` 中自带的 KaTeX 渲染；`archive/` 下的往期评测不会被改动。

`data/` 存放原始运行数据，其中的调用记录带有完整题面，**不得提交到公开仓库**（见 `.gitignore`）。

## 写作规则

**结构**

按以下顺序：
1. 摘要：一段，写出所有核心数字。
2. 引言：先用加粗引导的要点列出现有评测的不足，再列贡献，最后放概览图。
3. 相关工作：按主题分段，每段一个 `\paragraph`。
4. 基准：设计原则（要点）、题库组成表、构建流程与流程图。
5. 判题、计分与统计方法。
6. 实验设置：被测模型、调用设置（附表）、归因规则。
7. 实验结果：各小节标题写成问题，如「差距是否可信？」。
8. 成本与 token 效率。
9. 结论。
10. 局限性：不编号，用加粗引导的要点，只陈述事实。
11. 参考文献。
12. 附录：逐项明细、提示词、复现方法。
13. 末行：「由 Albert Huang 创建于 <日期>」。

**数字**
- 所有数字都由脚本从数据生成，不手填。
- 先看 `analysis.json`，再写正文。
- 区间用按题重抽样的 bootstrap（B = 2000，种子 0），模型之间用配对 bootstrap。
- 逐题比较用精确符号检验，得分相差不到 0.05 分记为持平。

**图**
- 配色用 Okabe-Ito，每个模型固定一种颜色。同一模型的另一组设置用同色加斜线或虚线。
- 字体用 Arial 加黑体，图宽 170 mm，子图标 a、b、c。
- 流程图只画黑色线框，不填色：一次性的构建步骤用实线框，每个模型都要执行的步骤用虚线框。
- 每张图都要转成 png 逐张看：图例不能遮挡数据，文字不能超出框，标签不能互相重叠。

**表**
- 用 booktabs 排版。行为「档位 × 模型」，列为指标。
- 每个指标列标出 ↑ 或 ↓，最高值加粗，方括号内为 95% 区间，$^{*}$ 表示显著。
- 表注写明规则，比如加粗的含义、区间的算法。

**内容**
- 被测模型：逐个写清能力与架构、厂商声称的具体技术改进及其针对的能力、官方自报成绩。每条都在一手来源上核实，并写进参考文献。
- 归因：先在实验设置里写明规则，判定分为「一致，可归因 / 不一致 / 超出测量范围 / 无法检验 / 无对应声称」。全文只说明一次：归因是观测上的一致，不是因果。
- 思考强度：列出每个模型实际用的档位，并说明一次 auto 的含义；不同档位的结果分别报告。
- 判题只用官方时限。必须报告输出 token、输出速度（tokens/s）与首个 token 时间。多个模型比较时，费用按各家官方美元标价计算。

**措辞**
- 每段结果先用一句加粗的结论开头，再给数字。
- 不写防御性或口语化的表达，也不写过程经历（重跑、超时重问、判题校准、接口故障等）。
- 没测的内容直接不写，不做解释。
- 结论必须与表格逐条一致。常见错误：一个模型例外时仍写「所有模型都……」；标题涵盖两个模型，事实只对其中一个成立。

**交付前检查**
1. 在正文中搜索「可能、只作、值得、这次、未测、宽时限、重跑、重问、切断、校准」。
2. 模型名用宏时，宏后面紧跟数字要写成 `\ds{} 20.4` 这种形式，否则空格会被吞掉。
3. 用 pdftotext 按页查每个浮动体的标题，确认没有表格落在「结论」或署名之后。
4. 很高的表格用 longtable，不用 `[H]`；「结论」之前加 `\FloatBarrier`。
5. 逐页转成 png 检查后再交付，PDF 按 `<日期>_<基准>技术报告_<模型>.pdf` 命名。
